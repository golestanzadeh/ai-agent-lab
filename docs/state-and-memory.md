# Case State and Run ID Model

Status: **foundational contract; runtime implementation introduced**

## 1. Purpose

Case State is the structured, case-scoped operational state of one tax case. A `run_id` identifies one execution attempt against exactly one `case_id`.

The model exists to make execution reproducible, resumable, auditable, and isolated. It is not an LLM conversation transcript and it is not a replacement for source documents or evidence.

## 2. Identity boundary

```text
person_id / entity_id
        ↓
   tax_period
        ↓
     case_id
        ↓
      run_id
        ↓
   case state
```

Rules:

- `case_id` is mandatory for all case-state operations.
- Every processing run has exactly one `case_id`.
- `run_id` is unique within the runtime and must never identify multiple cases.
- A cross-year operation may coordinate multiple case runs, but each run remains independently case-scoped.
- State must never be selected by filename, Drive location, or model context.

## 3. State model

The foundational state model records references and structured lifecycle information for:

- case identity and tax period;
- parties and household context;
- source documents;
- extracted evidence;
- normalized/reconciled facts;
- assumptions;
- rule references;
- calculations;
- optimization opportunities;
- challenges and unresolved conflicts;
- approvals;
- outputs;
- audit/run references.

The first runtime does not implement the full tax-domain schemas for all of these areas. It establishes the durable container and lifecycle boundary so later components cannot bypass case scope.

## 4. Run lifecycle

A run uses an explicit lifecycle:

```text
CREATED → RUNNING → SUCCEEDED
                  ↘ FAILED
                  ↘ BLOCKED
                  ↘ CANCELLED
```

A terminal run is immutable in its terminal status. A later attempt receives a new `run_id`.

`run_id` must be generated by deterministic runtime code, not by an LLM.

## 5. Idempotency

A caller may provide a stable `request_id`. Repeating the same request for the same case returns the existing run instead of silently creating duplicate execution state.

The runtime must reject an attempt to reuse a request ID for a different case.

Idempotency is execution-level protection. It does not imply that every downstream operation is automatically idempotent.

## 6. State transitions

The runtime validates legal transitions and rejects arbitrary jumps. At minimum:

- `CREATED → RUNNING`
- `RUNNING → SUCCEEDED`
- `RUNNING → FAILED`
- `RUNNING → BLOCKED`
- `RUNNING → CANCELLED`

Terminal states cannot be moved back to `RUNNING`.

## 7. Case-state mutation

State updates are always case-scoped and require the expected `case_id` and current `run_id` where execution state is involved.

A state object must not be writable through a generic global dictionary keyed only by document, person, or model session.

Material state changes should later carry provenance and audit references. The foundational runtime therefore keeps structured event references but does not yet implement the durable audit store.

## 8. Separation of concerns

```text
Source Documents  = authoritative source material
Evidence           = extracted/source-linked evidence
Case State         = operational structured state
Run Store          = execution identity/lifecycle
Audit Store        = durable reconstruction trail
LLM Context        = temporary reasoning context
```

LLM context may be reconstructed from authoritative state and evidence. It must never become the authoritative state store.

## 9. Failure behavior

Unknown `case_id`, invalid run ownership, invalid state transition, request-ID collision across cases, and writes against a terminal run must fail closed.

The runtime must not silently create an unscoped state object when case resolution fails.

## 10. Concurrency

The foundational in-memory runtime uses a lock around registry mutation. Future durable stores must preserve the same invariants under concurrent execution.

Concurrent runs for the same case are not automatically declared safe. Later orchestration rules must explicitly define which operations can run concurrently and which require serialization.

## 11. Persistence boundary

The current implementation is intentionally in-memory. It establishes the contract and tests before selecting a durable persistence technology.

Future durable state/run storage must preserve:

- stable IDs;
- case isolation;
- request idempotency;
- lifecycle history;
- schema versioning;
- timestamps;
- audit linkage;
- recovery semantics.

Google Drive may store artifacts, but it must not become an implicit database for runtime state.

## 12. Security invariant

> No Case State or Run State may be created, read, mutated, or resolved without a validated `case_id` boundary.

Cross-case contamination is a security and correctness failure and requires dedicated automated tests.

## 13. Explicitly deferred

This foundational step does not yet implement:

- durable database selection;
- distributed locking;
- full tax-domain state schemas;
- event sourcing;
- workflow queueing;
- checkpoint/resume orchestration;
- durable audit store;
- Google Drive state persistence;
- CASE-001 migration;
- multi-user authorization.

These are later implementation layers and must not be smuggled into the foundational model by accident, because software projects already have enough accidental architecture.

## 14. Acceptance criteria

The model is acceptable when:

1. every run has one case;
2. run IDs are unique;
3. request IDs are idempotent per case;
4. request-ID reuse across cases is rejected;
5. unknown cases cannot create state;
6. run lookup is case-scoped;
7. legal lifecycle transitions are enforced;
8. terminal runs cannot be mutated;
9. state records retain schema and timestamps;
10. cross-case reads/writes are rejected;
11. LLM context is not authoritative state;
12. the runtime can later be replaced by a durable store without changing the case/run identity contract.
